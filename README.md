# Mission Sync — phase 1 (sync core)

The sync engine from the [design doc](https://claude.ai/code/artifact/5d9c89c9-2e7f-4514-a96b-71bfd37fb841), proven on a stand-in domain before any real mission features or UI move over. See the [migration doc](https://claude.ai/code/artifact/bd6bc009-563e-432b-bbce-04dde518f554) for the phase plan.

Phase 1 gate: **convergence and network tests pass.**

## Layout

| Path | Package | What it is |
| --- | --- | --- |
| `packages/sync-core` | `@sync/core` | Shared by client and server: records, `Tx`/overlay, `defineMutation`, wire protocol, client activity state (optimistic apply + rebase), clock sync |
| `packages/sync-client` | `@sync/client` | `SyncClient` (connection, reconnect/backoff, ping, batching, persistence), WebSocket transport, IndexedDB persistence, React hooks (`@sync/client/react`) |
| `packages/sync-server` | `@sync/server` | `ActivityActor` (one per activity, serial apply, per-view fan-out), `Hub` (connections → actors, one-time reads, idle unloading), storage interface + in-memory storage |
| `packages/domain` | `@sync/domain` | The activity model (missions, trainings and other activities): records, queries, mutations, field projections. Shared by `web` and `server`; the server and harness run on it |
| `packages/model` | `@sync/model` | Prototype UI model: MobX store fed from client snapshots, field and command models (`FieldActivity` ← `CommandActivity`, ...) over the domain queries, a server clock, and a React provider (`@sync/model/react`) |
| `server` | `server` | Hono app: `/api/sync` WebSocket, `/api/bootstrap` (site name and colors), `/health`, dev debug endpoint, static UI, and `summaries.ts`, which keeps the activity list and archive current. `build.mjs` bundles it to `dist/index.mjs`. Auth and REST land here |
| `web` | `web` | The app: `src/shell` (site config, theme, dev sign-in, the session's `SyncClient`, toolbar, routes), `src/sections/{field,ops,reports,admin}` (ops, reports and admin load lazily), `src/ui` shared components. MUI and wouter, as in the legacy app. Every page is ported; see [web/README.md](web/README.md) |
| `test/harness` | `harness` | Test harness: side-by-side command, member and external clients on the real domain (through `@sync/model`), with per-client latency and offline switches, pending queue, rejections, message log |
| `packages/*/__tests__` | | Unit tests next to their package: rebase and `testDomain.ts`, a small people-and-statuses domain the engine tests share (`sync-core`), storage and the Postgres suite (`sync-server`), activity rules and projections (`domain`) |
| `test/integration` | | Tests across packages: seeded convergence simulation (4 clients, 20 seeds) with variable latency, jitter and dropped connections, in-order delivery like TCP; the activity domain on the real activity actor; summaries in the list and archive; activities opened not live |
| `test/smoke.ts` | | End-to-end check against a running server over real WebSockets |

Planned, not created yet:

- `packages/devtools`: `SyncPanel`, the in-app panel for connection state and outstanding changes, also used by the harness.

## Commands

Requires Node 22.12+ and **npm 11** (npm 10 crashes resolving this tree's peer dependencies). Use `npx npm@11 install` if your global npm is older.

```sh
npm install
npm run db               # Postgres 18 in Docker, host port 5433
npm run seed -- server/organizations.dev.json  # import organizations into DATABASE_URL (see below)
npm test                 # unit, convergence and storage tests (Postgres suite runs when the db is up)
npm run typecheck
npm run dev              # starts the db, the web app on :4000, API server on :5174 behind Vite's proxy
npm run dev:harness      # same, with the harness on :4000 instead of the web app
npm run build            # dist/index.mjs (server, all deps bundled) + dist/public (the web app)
npm run start            # node dist/index.mjs: UI and API on :4000 (set DATABASE_URL, else in-memory)
docker compose up --build  # app + Postgres; app on :4000 (APP_PORT to change the host port)
npm run smoke            # end-to-end check against :4000; needs a server with DEV_TOOLS=true
```

**Ports.** The browser uses port 4000: `http://localhost:4000` is the dev umbrella organization's site, and `http://crt.localhost:4000` and `http://rmr.localhost:4000` its units' (browsers resolve `*.localhost` to this machine). In dev, Vite forwards `/api/**` (WebSocket included) and `/health` to the server on `:5174`, keeping the `Host` header (`server/.env.development`; `SYNC_LOG=1` logs every message). Dev settings come from the environment, then `server/.env.local` if it exists (git-ignored: put `SECRETS_KEY` here), then `server/.env.development` (committed defaults).

**Routes.** `/api/sync` (WebSocket), `/api/bootstrap`, `/api/icon/<size>.png`, `/api/icon/maskable/<size>.png` and `/api/manifest.webmanifest`, `/api/auth/*`, `/api/activities` and `/api/activities/:activityId`, `/api/activities/:activityId/grants/:personRef`, `/api/admin/*`, `/api/debug/activities/<activityId>?view=command|field:member|field:external` (only with `DEV_TOOLS=true`), `/health`. Anything else serves the UI, falling back to `index.html` for client-side routes. Every `/api` route is for the site its hostname names, and is a 404 for a hostname no organization has.

**Organizations and sites.** Organizations form a tree, an umbrella over its units (`server/src/organizations.ts`, schema in `packages/domain/src/organizations.ts`). Each has hostnames: a request's site is the organization with its hostname, and `/api/bootstrap` gives its title, partners and brand. Partners (the organizations it may create missions or events for) are its own and its ancestors'; its own entry for a partner, or a nearer ancestor's, sets what it may create for them. The brand (colors and app icons, served at the sizes the app uses and in the install manifest), the member provider and the sign-in provider are the organization's own, or else the nearest ancestor's. They live in the `organizations`, `member_providers`, `sign_in_providers` and `site_admins` tables (in memory without `DATABASE_URL`, where the server starts with none, so every site is a 404).

**Seeding.** The server never reads a seed file. `npm run seed -- <file>` imports one into `DATABASE_URL` (from the environment, else `server/.env.local`, else `server/.env.development`, so the dev database by default): each member provider, sign-in provider and organization in the file replaces the stored one with its id, and its site admins are added. Nothing else is changed or removed, so it's safe to run again, and an import that doesn't hang together writes nothing. A provider without a `clientSecret` keeps the stored one (secrets are encrypted with `SECRETS_KEY`, so that must be set to import one). Restart a running server to see the changes. `server/organizations.dev.json` is a fictional umbrella (Cascade Valley SAR Council) over CRT and RMR; for real organizations, use a git-ignored file of your own. The `docker compose` app uses the same database as `npm run dev`.

To start the organizations over, keeping activities, empty their tables, seed again and restart the server:

```sh
docker compose exec postgres psql -U sync -d sync -c "TRUNCATE organizations, member_providers, sign_in_providers, site_admins"
npm run seed -- server/organizations.dev.json
```

To start everything over, activities and locations included: `docker compose down -v` (removes the Postgres volume), `npm run db`, then seed.

**Sign-in.** Sessions are server-side (`sessions` table, a day long), behind an HTTP-only cookie that belongs to one hostname, so signing in on one site doesn't sign you in on another. People sign in with Google, through the site's sign-in provider (see below): `/api/auth/login?then=<path>` sends the browser to Google, and `/api/auth/callback` finishes (`server/src/google.ts`: the code flow with PKCE and a nonce; the ID token comes straight from Google, so its claims are checked but not its signature). Only someone the member directory knows may sign in, for now (visitors will come by invitation); a refusal goes back to the app as `?signinError=`, which the login panel shows. Signing in looks the email up in the member directory: the provider for the organization with the email's domain, up the tree, or else the site's own. Their tier comes from their groups there, by the member tiers of their organizations (the same ones whose member tags they get): the highest wins, and anyone without one, or not in the directory, is field. The limits of that tier are for missions only: members manage trainings and other events as command (for now), and may create them; only command may create a mission, or make an event one. On a mission, someone at command can grant a person on its roster command there (`PUT /api/activities/:activityId/grants/:personRef`; `DELETE` takes it away), stored in `activity_grants`. A grant counts on that mission only: its ops dashboard, the command parts of its field pages, and granting others there, but not creating missions. The session keeps the tier from their groups, with their grants beside it. Who someone is on an activity is worked out per activity, on the server (`Projector.viewerIn` for the kind, the connection's `viewerIn` for grants) and alike on the client; without a grant or an event, by far the usual case, they're the connection's own viewer. A change to someone's grants updates their stored sessions and closes their connections, and a change of kind that changes someone's view closes theirs: their client reconnects, says which view its copy is in, and gets the activity afresh in the new one. A change in D4H counts from the next sign-in. Whoever's organization they belong to, they're signed in on the site's terms and respond under the site's organization. With `DEV_TOOLS=true`, the server offers `POST /api/auth/dev`, which signs in any email at the tier their groups give (or a chosen one) and a chosen class, and takes someone the directory doesn't know as a visitor (`adhoc:<email>`) given a name. Given a `personRef` and a name, it impersonates that person without asking the directory. With `?token=1` it returns the session id instead of setting the cookie, and the server takes it as `?session=` on any route, so the harness's panes can each be someone different in one browser. The WebSocket and the member, location and weather routes need a session.

**Admin.** `/admin/organizations`. Site admins (`SITE_ADMINS`, comma-separated emails, plus a list kept on the page) can change everything: organizations (and their place in the tree), member and sign-in providers and the stored site admins, though not the hostname they're on or the organization whose site it is (change those from another site). An organization's admins (listed on it) can change its settings, and those of the organizations under it: titles, brand, member tags and tiers, what it may create, partners and admins, but not hostnames, email domains, parent or provider. Member providers' client secrets are stored encrypted (AES-256-GCM) under `SECRETS_KEY`, 32 random bytes in base64 (`node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`); the page can set a secret but never shows it. Without `SECRETS_KEY`, providers with secrets can't be saved or used; losing it means entering the secrets again.

**Sign-in providers.** A sign-in provider is a Google OAuth client (a Web application in a Google Cloud project): its client id and secret, the secret stored encrypted. Set on the top organization, every site under it signs in with the same client; an organization elsewhere in the tree, or another tenant, names its own. The client lists each site's `https://<hostname>/api/auth/callback` as an authorized redirect URI, so a new site hostname means adding one. Google allows `http://localhost:<port>` redirects but not `crt.localhost`, so on a dev machine every site uses one callback, `SIGN_IN_CALLBACK=http://localhost:4000/api/auth/callback` (in `server/.env.development`; add it to the client's redirect URIs). The sign-in's state names the site that started it, and the callback sends Google's code on to that site's own `/api/auth/callback`, only if it's one of ours (the callback's host needn't be a site itself); that site finishes, with the PKCE verifier from its cookie, so a code sent elsewhere is no use.

**App icons.** A brand's icons are stored by size (512, required, and optionally 192, 180 and 32), each a `data:image` URI or an `https://` URL, with an optional `maskable` set of the same sizes whose content keeps to the middle 80% so phones can crop it to a shape. `/api/icon/<size>.png` (32 for the favicon, 180 for the apple-touch-icon, 192 and 512 for the manifest) is made from the smallest stored icon at least that big, or else the largest, scaled down and padded to a square PNG with Jimp (`server/src/icons.ts`, kept in memory once made, with an ETag). `/api/icon/maskable/<size>.png` comes from the maskable set, or the plain one when there are none, and the manifest only offers maskable icons when there are some: a plain icon offered as maskable gets clipped. An icon Jimp can't read (an SVG, as the dev seed's) is served as stored.

**Members.** A member provider is cedar, our API in front of D4H (`../../cedar`, see its API.md), or a fixture of fictional members. A provider's id is the prefix of its people's person refs (`kcsara:1234`), so member info goes to the right one. Add Responder searches `GET /api/v1/organizations/:orgId/members?query=` (3 to 100 characters, as the legacy route): cedar's D4H passthrough finds operational members (`/api/d4h/v3/members?search=`), and cedar's own model (`/api/v1/members/:id`) gives their names, groups and units. Only members of the organization's unit in cedar (its "unit in provider") are listed; an organization without one lists everyone. Photos (`/api/v1/organizations/:orgId/members/:memberId/photo`) come through the passthrough's member image. Once someone is on an activity, the server looks them up and writes their tags (their groups, as labelled by their organizations' member tags: those of their unit in the provider, and of organizations on the provider with no unit) and phone and email (`setMemberInfo`), once per person per server run. A cedar provider needs cedar's URL, Hydra's token endpoint (`<issuer>/oauth2/token`) and a client-credentials client with `members.read` and `d4h:members.read`. Tests are in `server/__tests__`, against a fake cedar.

**Saved locations.** The location catalog is plain REST, as in the legacy app (it doesn't need to be live or offline): `GET /api/v1/locations?query=` (by title; all for an empty query), `PUT /api/v1/locations` and `DELETE /api/v1/locations/:id`. It's a `saved_locations` table beside the activity tables, or in memory without `DATABASE_URL`. Any signed-in person may change it, as in the legacy app.

**Weather.** The ops dashboard's forecasts come from `GET /api/weather?lat=&lon=`, the legacy route: the server asks NOAA (`api.weather.gov`) for the point's hourly forecast and returns the current period, or a 502 with the reason. NOAA covers the US only.

**Activity list.** The list Home shows is a sync scope of its own, `$activities`, holding a summary of each open or recent activity: not closed, starting in the future, or ended in the last 14 days (`inActivityList`; the legacy app's rule, with 14 days for its 90), so it stays in the tens. Clients open it like an activity, so it's live, versioned and cached offline; only the server writes it. Every activity's summary is also in a second scope, `$archive`, which clients don't open: `GET /api/activities` returns it, for the Mission and Event Lists and anyone else downloading activities. After an activity commits, the server recomputes its summary after a trailing 2 s debounce (capped at 5 s) and writes it to each scope where it changed. Hourly, and on startup, it drops activities that have aged out of the list. On startup it also adds summaries for stored activities missing from the archive, loading each of those once, ever.

**Completed activities.** `GET /api/activities/:activityId` returns an activity as the viewer sees it (the records a subscription starts with, its version and view), or a 404. The app opens an activity live only while the list has it open. A closed one (or one the list doesn't have, closed long ago) is read once that way, not subscribed to and not kept offline; it goes live, carrying on from the version it read, when the list shows it open again (someone reactivated it) or when a change is made to it on the page. An activity no one is subscribed to leaves the server's memory after 5 idle minutes and is loaded again when something needs it; work that arrives as it unloads is retried on a fresh copy.

**Storage.** `DATABASE_URL` selects Postgres; without it the server uses in-memory storage (and warns in production). Each commit is one transaction covering records, per-client mutation ids and the mutation log, guarded by the activity's version so a second process writing the same activity fails with a conflict instead of overwriting. Tables (created on startup if missing): `activity_meta`, `records` (each record whole as `jsonb`), `client_mutations`, `mutation_log` (append-only; `seq` orders it). Dev uses `postgres://sync:sync@localhost:5433/sync`; storage tests create and drop a `sync_test_*` database per test (`TEST_DATABASE_URL` to point elsewhere).

**Deploy artifact.** `dist/` is self-contained: `node dist/index.mjs` needs no `node_modules`, and serves `public/` from next to itself (override with `UI_DIST`; port with `PORT`). The Docker image contains only `dist/` and runs as `node`.

## Phase 1 shortcuts (deliberate, to revisit)

- **Auth:** only people the member directory knows can sign in (visitors will come by invitation), and the tier from member groups is as of sign-in. Signing out ends this site's session, not Google's.
- **`DEV_TOOLS=true`** turns on the dev sign-in, `?session=` tokens and the debug route. It's never implied by the build: only `server/.env.development` and `docker-compose.yml` (for trying the image locally) set it. Never set it on an internet-facing site.
- **Any client may open any activity.** One that doesn't exist (no change has applied to it) gets an empty reset at version 0, which the client takes as "not found" unless it's creating it; nothing is stored for it until a change applies, so rejected pushes to an unknown id leave no trace.
- **Not yet built:** cross-actor commit batching (~10 ms), build-version `reload`, HTTP fallback transport, `permessage-deflate`, the cross-activity outbox, keeping activities to their organization tree (the list shows every activity to everyone).
