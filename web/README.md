# web

The app people use. It replaces respond-next's client, keeping its URLs and, page by page, its DOM. The legacy app's components move over with their JSX; what changes is where they read data (the `@sync/model` models) and how they act (model methods, which call `client.mutate`).

## Layout

| Path | What it holds |
| --- | --- |
| `src/shell/App.tsx` | Loads `/api/bootstrap`, themes the app, gates it behind sign-in, starts the session's SyncClient, renders the routes. `useSite()` gives the site config |
| `src/shell/auth.tsx` | The session (`useAuth()`): who is signed in, `signIn`, `signOut` |
| `src/shell/sync.tsx` | One `SyncClient` per session (`useSyncClient()`), kept offline-ready in IndexedDB, one store per user and tier |
| `src/shell/ActivityLayout.tsx` | Opens an activity for the pages under it; they read it with `useFieldActivity()` or `useCommandActivity()`. Shows "Loading activity..." until it arrives, and "Activity not found" when the server doesn't have it or it was removed |
| `src/shell/ToolbarPage.tsx`, `AppMenu.tsx` | The legacy page frame: app bar with title, connection icon and account menu |
| `src/shell/routes.tsx` | The legacy URLs: `/`, `/mission/*`, `/event/*`, `/ops/:id`, `/reports/*`, `/admin/*` |
| `src/sections/field` | Home (My Activity, Missions, Events, from the activity list; each active tile has its status button) and the activity page (`/mission/:id`, `/event/:id`): desktop and mobile layouts, briefing and manager panels, unit chips, roster with the participant dialog, the status button and its confirm form, ETA and miles. New and Edit (`/mission/new`, `/mission/:id/edit`, and the event ones) with the location picker and dialog. Loads with the shell |
| `src/sections/reports` | The Mission List and Event List (`/reports/missions`, `/reports/events`): a data grid of the activity list. The roster report (`/reports/roster/:id`): a row per stint from each person's status timeline (`rosterEntries.ts`; someone added straight to staging or an assignment starts a stint there, that time standing in for the sign in), with standby rows, last-name-first, column borders, CSV download and print. Loads the first time its route is visited |
| `src/sections/admin` | The saved-location catalog (`/admin/locations`): find, create, edit (with its description) and delete. Organizations (`/admin/organizations`, in the account menu for admins): their settings, and for site admins member providers and site admins too. Loads the first time its route is visited |
| `src/ui/locations` | The location picker (searches the catalog), the location form, and the activity's location dialog ("Create/Update Saved Location"), shared by New/Edit activity and admin |
| `src/sections/ops` | The ops dashboard (`/ops/:id`, command and support): header with clock and responder counts; the resource pool (responders, and the equipment catalog to drag from); teams with status, GAR, leader, members and equipment; the comms log with search, favorites, edit, delete and print; groups, places, the description, NOAA weather and the equipment summary. People and equipment move by pointer drag and drop (`dnd.tsx`, mouse or touch). Under 1280px wide it's a read-only phone view; up to 1920px teams and comms share a tabbed panel. `opsRules.ts` holds its orders, counts and suggestions. Loads the first time its route is visited |
| `src/ui` | Shared components with no data of their own, mostly the legacy ones as they were (`OutputForm`, `SplitButton`, `RelativeTimeText`, ...); `status.ts`, the legacy words and colors for each status; `useChange`, which runs a change and shows why if it's refused; `activityPath` |
| `src/shell/dialogs`, `preferences.tsx` | The legacy dialog provider (`useDialogs()`: `open`, `confirm`, `alert`) and per-device preferences |

## Rules

- **Sections don't import each other.** Each may use the shell, `ui`, its own files and the packages. The shell imports a section only through its `index.ts`. `__tests__/boundaries.test.ts` checks both, until ESLint's boundary rules are set up.
- **Read through the models,** inside `observer(...)`. A component that reads the model without `observer` renders once and goes stale.
- **Use `activity.clock` or `client.now()` for "now",** never `Date.now()`: it's the server's clock.

## Sign-in for now

The login panel offers Sign in with Google when the site has a sign-in provider (`googleSignIn` in the site config); it goes to `/api/auth/login` and comes back to the same page, or with `?signinError=`, which the panel shows once. When the server has `DEV_TOOLS=true`, it also offers the dev sign-in, a button that opens its form: an email (looked up in the member directory, as Google sign-in does), a name for someone the directory doesn't know, the tier (from their groups, by their organizations' member tiers, unless one is picked) and the class. The server keeps the session and the browser its cookie, which goes with the WebSocket too. A copy of the session is kept in `localStorage` so the app opens signed in while offline; the server's answer replaces it when there is one. With neither, it says sign-in isn't available. Someone at command on a mission sees Grant command (or Remove command grant) in a roster member's dialog there; it counts at once, as the server closes the grantee's connection and they reconnect as command there. Members are command on trainings and other events. The sync client works out who it is on each activity from the view the server labels its records with and the activity's kind (`clientViewerOn`), and `ActivityModelProvider` makes the model anew (`FieldActivity` or `CommandActivity`) when that changes. New Mission goes by the tier from their groups; New Event shows for members too.

## Not here yet

- **Ops dashboard:** comms are only what people log; respond-next also logged team status and GAR changes automatically, which the mutation log already records. Its "hide automated" filter still hides the automated entries imported from respond-next. The first person dropped on a team without a leader leads it (respond-next's leader was the first member). A place's weather is for the place's own coordinates (respond-next showed the activity's). Places list Command Post and Field first, then by name. Staff roles (respond-next's `staff`, unused by its dashboard) aren't ported.
- **Locations:** an activity's location remembers the saved location it came from (`savedId`); changing it for the activity only drops that link. The activity dialog doesn't show a saved location's description (an activity doesn't keep one) and leaves it alone when updating; the admin page edits it. There's no warning when someone else is drafting the same new activity (the legacy app used presence). A new event is a training; editing keeps an existing event's kind. A partner that owns a new activity is listed as invited.
- **Member photos** come from `/api/v1/organizations/<unit>/members/<id>/photo`, through cedar (see the root README). The fixture directory has none, so in dev the participant dialog shows a broken image.
- **Home and the lists show every activity to everyone,** in every organization tree. New Mission shows for command and support, and New Event for members too, when the organization or a partner may create that kind.

`activityEdit.test.tsx` covers creating a mission (new location, partner owner, units), the owner choices per type, editing, and a field member refused. `roster.test.tsx` covers the roster report live, and `rosterEntries.test.ts` its stint rules and CSV. `opsDashboard.test.tsx` covers the ops dashboard: the header, pool, places and weather; adding a team, dragging someone onto it and back, and its status; editing a team (a taken name refused); disbanding a team with people on it; adding a place (coordinates checked) and a group, with a leader dropped on it; naming a custom item on drop and the staged summary; the comms log; the description; marking a team member assigned; and the phone view. `opsRules.test.ts` covers its orders, name checks and coordinate finding. `organizationAdmin.test.tsx` covers a visitor's sign-in and the organization admin page: an organization admin's limits, app icons by size (a 512 one needed), a site admin adding a provider (its secret kept back) and an organization, and the site admin list. `signIn.test.tsx` covers the login panel: Sign in with Google where the site has a provider, a refusal shown once, and the dev sign-in beside it. `grants.test.tsx` covers granting command on a mission, and members managing trainings.
